# 首屏动画抖动、闪动与掉帧问题总结

> 整理日期：2026-07-18  
> 涉及范围：桌面端 Banner、自动下滑入场、图片视差、页面卡片、导航栏、波浪与樱花效果

## 1. 问题表现

首屏刷新或从其他页面返回时，主要出现过以下现象：

- 中间 Banner 在自动下滑过程中轻微上下抖动。
- 首屏中间区域偶尔闪动或短暂没有图片。
- 快速滚动时图片有撕裂感，自动入场时存在卡顿和掉帧。
- 某些调整虽然降低了抖动，却会改变原有的卡片上浮观感。

这些现象并非由单一 CSS 参数引起，而是图片加载、多个动画时钟和 GPU 合成压力共同造成的。

## 2. 核心原因

### 2.1 多套动画同时控制画面位置

入场期间曾同时运行以下逻辑：

1. `ArchiveHeroBanner` 使用 `requestAnimationFrame + window.scrollTo` 自动滚动页面。
2. `Hero` 监听原生 `scroll`，再通过另一套 `requestAnimationFrame` 平滑图片视差。
3. 页面卡片使用独立的 CSS 上浮动画。
4. 导航栏在每次滚动后计算透明度。
5. 四层波浪持续进行 SVG 位移动画。
6. 用户启用樱花效果时，Canvas 仍在逐帧绘制粒子。

浏览器派发原生 `scroll` 的时机不一定与自动滚动帧完全一致，因此同一帧附近可能发生两次图片 `transform` 写入，产生轻微位置抖动和额外重绘。

### 2.2 Banner 图片优化请求间歇失败

开发日志中出现了大量类似错误：

```text
The requested resource isn't a valid image for /assets/desktop-banner/d1.webp received null
```

8 张 Banner 都曾通过 Next.js 图片优化器出现空响应。轮播透明层切换时，如果目标图片没有可绘制内容，就会表现为中间闪白或闪动。

原始 WebP 文件本身可以正常返回 `200 image/webp`，问题集中在开发环境的 `/_next/image` 优化链路，而不是图片文件损坏。

### 2.3 首次载入时强制重启动画

原实现首次挂载时会执行以下流程：

1. 把页面卡片的 `animation` 设置为 `none`。
2. 读取 `offsetHeight` 强制同步布局。
3. 下一帧移除内联样式，重新启动 CSS 动画。

这会让卡片先以最终位置绘制一帧，然后跳回动画起点再上浮，形成明显的闪动。React 开发环境严格模式会重复执行 Effect 生命周期，使该现象更容易被观察到。

### 2.4 不可见轮播图仍消耗解码和合成资源

早期版本会同时挂载全部 8 张全屏 Banner。第一次性能优化将其减少到当前图和相邻图，但入场期间仍会同时加载、解码 3 张大图。

即使相邻图片的 `opacity` 为 `0`，它们仍可能参与图片解码、绘制准备和 GPU 合成。与自动滚动、卡片动画同时发生时，会挤占每帧约 16.7ms 的渲染预算。

### 2.5 常驻 `will-change` 并不适合超大图片层

给整个超大 Banner 长期设置 `will-change: transform` 会强制保留大型 GPU 纹理。它没有解决动画时序问题，反而可能增加显存压力，使部分设备上的抖动和掉帧更明显，因此最终没有保留。

## 3. 最终处理方式

### 动画时序

- 自动入场由 `ArchiveHeroBanner` 提供唯一的同步帧。
- 入场期间 `Hero` 忽略稍后到达的原生 `scroll` 事件，避免重复写入图片位置。
- 图片位移按设备物理像素对齐，减少半像素重采样造成的细微颤动。
- 正常手动滚动时仍使用平滑视差，不改变原有交互方向。

### 图片加载

- 本地 Banner 直接加载现有 WebP，不再经过 `/_next/image`。
- 首屏入场期间只挂载并解码当前 1 张 Banner。
- 相邻图片在 1.5 秒后再挂载，避开自动入场的关键帧窗口。
- 非当前、非过渡图片使用 `visibility: hidden`，避免透明预加载层参与合成。

这里的取舍是：直接 WebP 的单次传输体积可能高于 Next.js 动态优化结果，但加载链路更稳定，不会再因为优化器空响应而闪白。

### 其他动画和计算

- 自动入场期间暂停四层波浪动画。
- 用户开启樱花效果时，入场期间暂停 Canvas 实际绘制。
- 导航栏入场期间跳过无意义的逐帧透明度计算。
- 删除首次载入时的卡片动画强制重启，只在浏览器缓存恢复场景处理动画恢复。

## 4. 当前资源情况

桌面 Banner 源文件约为：

| 文件 | 分辨率 | 大小 |
| --- | ---: | ---: |
| d1.webp | 2048×1152 | 500 KB |
| d2.webp | 2000×1200 | 316 KB |
| d3.webp | 2560×1440 | 212 KB |
| d4.webp | 3840×2160 | 527 KB |
| d5.webp | 5856×3904 | 901 KB |
| d6.webp | 1920×1080 | 364 KB |
| d7.webp | 1920×1080 | 363 KB |
| d8.webp | 2880×1620 | 277 KB |

其中 `d5.webp` 的解码尺寸明显偏大。它不会再影响首次入场，但轮播到该图片时仍可能在低显存设备上产生瞬时压力。

## 5. 验证结果

- ESLint 检查通过。
- TypeScript 类型检查通过。
- 首页、分类页、音乐馆、相册和游戏页正常返回 200。
- 首屏服务端输出的 Banner 图片节点由最初 8 个降低到 1 个。
- Banner 已直接输出 `/assets/desktop-banner/*.webp`。
- 稳定运行一轮后，没有新增 Banner `isn't a valid image` 错误。

后端 `127.0.0.1:8000` 未启动时，头像和文章接口仍会报错；这属于后端资源不可用，与本次 Banner 动画问题不是同一原因。

## 6. 后续优化建议

如果仍需继续提高低端设备或高分辨率屏幕上的帧率，建议按以下顺序处理：

1. 将 `d4.webp`、`d5.webp` 和 `d8.webp` 重新编码到最高 2560px 宽，并保留原图备份。
2. 在生产构建中使用 Chrome Performance 录制一次完整入场，重点查看 Long Task、Image Decode、Paint 和 Composite Layers。
3. 避免在 Banner、页面大容器或导航栏上新增大范围 `blur`、`filter`、阴影动画和常驻 `will-change`。
4. 如果 JavaScript 自动滚动在部分设备上仍不稳定，再考虑改为浏览器原生 Scroll-driven Animation，但需要单独验证浏览器兼容性。
